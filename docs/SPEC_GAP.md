## 0. 한 줄 요약

현재 코드는 **"지도 1화면 + 도감 팝업"** 구조이고, 기획/와이어프레임은 **"홈 + 4~5탭 GNB + 지도 / 도감 / AI 리포트 / AR + 카드 오버레이 시스템"** 구조다.
지도·GPS·해금 판정·방문기록 저장이라는 **하부 엔진은 이미 완성도 높게 구현**되어 있고, 그 위에 얹을 **화면·UI·AR·AI·백엔드가 통째로 비어 있다.**

## 2. 확정된 목표 구조 (기획 + 와이어프레임 종합)

```
로딩(유니티 로고 → PixelRoad 로고 + 진행률)
        ↓
      Home  ─ 헤더(로고/현재위치/설정) · 발견한 랜드마크 n/30 · 도감 진행률 % · [바로 탐험 시작하기]
        │
  ┌─────┼─────────┬──────────────┬──────────┐
 지도    도감      AI 탐험 리포트    AR
  │      │             │            │
  │      └ 카테고리 필터 → 2열 그리드 → 라지 카드(앞/뒤)
  │
  ├ 랜드마크 마커 + 남은거리 + 잠금/해금 배너 → [카드 보기] → 랜드마크 카드(앞/뒤)
  ├ 해금 반경 진입 → "랜드마크 발견! [OO]" 팝업 → [확인]
  └ AR 반경 진입 → GNB AR 활성화 → AR 화면(전체 탐색 / 집중 모드)
```

GNB 탭: 와이어프레임 1페이지는 **4탭(지도/도감/AI탐험리포트/AR)**, 최신 `_ar작업중` 페이지는 **홈이 추가된 5탭(홈/지도/도감/AI탐험리포트/AR)** → **§6-1 결정 필요**

### H. AI 탐험 리포트 + 백엔드

**H-1. 백엔드 (NestJS) — 리포지토리에 없음. 신규 구축**

```
POST {서버}/api/report
Content-Type: application/json

Request
{ "visitedLandmarks": [ { "landmarkId": 1, "visitCount": 2 }, ... ] }

Response 200
{
  "title": "철도 탐험가",
  "analysis": "철도와 교통 거점을 중심으로 탐험하는 성향입니다.",
  "recommendations": ["대전역", "부산역", "광명역"],
  "summary": "철도를 따라 전국을 탐험하는 스타일입니다."
}
400 Bad Request / 500 Internal Server Error
```

- NestJS가 `landmarks.json`을 **서버에도 보유**하고 `landmarkId`로 상세 조회 → Prompt 생성
- LLM: **Hugging Face / Gemma** (Llama·Qwen 대안)
- Prompt 말미에 JSON 강제 지시:
  `반드시 아래 JSON 형식으로만 응답하세요. { "title":"", "analysis":"", "recommendations":[], "summary":"" }`

## 5. 권장 작업 순서

1. **A. 앱 구조 + GNB** — 이게 없으면 나머지 화면을 붙일 자리가 없다
2. **C. 홈** + **B. 로딩** (구조 검증용 최소 화면)
3. **E. 랜드마크 카드** (지도·도감 양쪽에서 재사용 → 먼저 만들면 이득)
4. **D. 지도 UI 보강** (배너 / 해금 팝업 / 거리 표시)
5. **F. 도감** (필터 + 그리드 + 카드 연결)
6. **I. 데이터 정합화 + K. 에셋** (병행 가능, 디자인 담당)
7. **H. 백엔드 + AI 리포트** (백엔드는 Unity와 병렬 진행 가능)
8. **G. AR** (리스크 최대, 담당자 분리)
9. **L. 빌드/제출 정리**

병렬화 포인트: `A→C→E→D→F`(Unity 클라) / `H-1`(백엔드) / `G`(AR) / `I+K`(데이터·아트) 4트랙.

## 6. 결정이 필요한 미정 사항 (TBD / 스펙 충돌)

| # | 항목 | 충돌 내용 |
|---|---|---|
| 6-1 | **GNB 탭 개수** | 와이어프레임 1페이지 = 4탭(지도/도감/AI/AR), `_ar작업중` = 5탭(홈 추가). 홈을 탭으로 둘지 진입 화면으로만 둘지 |
| 6-2 | **설정 화면** | 홈 주석에 `설정버튼 → AR 반경 설정`만 있고 설정 화면 자체가 미설계 |
| 6-3 | **도감 수집률 게이지** | 도감 표 7번에 `⇒ 빼도 됨!!` 메모. 넣을지 결정 |
| 6-4 | **카테고리 체계** | 현 데이터 `station/culture/history/public` ↔ 와이어프레임 필터 `역사/문화/생활/교통/자연/관광/기타` ↔ 기획서 `궁궐/박물관/역` |
| 6-5 | **AI 리포트 갱신 시점** | "랜드마크 해금될 때마다 자동"(Notion) ↔ `탐험 분석하기` 버튼(와이어프레임). 해금마다 LLM 호출은 비용/지연 리스크 |
| 6-6 | **탐험기록 없음 화면** | 주석에 "해금 1개 이상 전에는 디저블 상태이면 현 화면 필요없음" — 만들지 결정 |
| 6-7 | **폰트** | 기획/디자인 = Pretendard(본문) + 픽셀 폰트(제목), 현재 프로젝트 = Galmuri11 단독 |
| 6-8 | **컬러 토큰** | 와이어프레임에 명시된 HEX는 `8E8E8E` 하나뿐. 정식 팔레트 확정 필요 |
| 6-9 | **해금 반경 / AR 반경 수치** | 와이어프레임 원문이 `반경 ?? m`, `AR 반경 = 해금반경 + ?m`로 **미정**. 기획서엔 50m, 50~100m, `visitRadius` 80/50 혼재 |
| 6-10 | **카드 규격 충돌** | 디자인 시스템 보드 `Landmark Card_앞면 1000×220 / 이미지 200×200` ↔ 카드 규칙 `라지 840×1120 / 이미지 792×560`, `스몰 360×480 / 312×230` |
| 6-11 | **`quizScore`** | AI API 설계 문서에 퀴즈 점수 필드가 등장하나 **퀴즈 기능은 MVP 제외**이고 구현도 없음. API 스펙에서 제거 여부 |
| 6-12 | **AI 응답 필드명** | `{summary, recommendation}`(MVP_v1.1) ↔ `{travelerType, analysis, recommendations, summary}` ↔ **`{title, analysis, recommendations, summary}`(API 명세서 v1.0 = 최신)** |
| 6-13 | **`era` vs `collectionTitle`** | 초안은 `era`, v1.1은 `collectionTitle`. 코드는 `collectionTitle` 사용 중 |
| 6-14 | **360° 뷰 범위** | 기획서상 Phase 2인데 와이어프레임 카드에는 360° 버튼이 이미 들어가 있음 |
| 6-15 | **탭 라벨 표기** | `탐험 도감`/`AR 탐험` ↔ `도감`/`AR` 혼재 |
| 6-16 | **서버 주소** | API 명세 Endpoint가 `서버지정주소/api/report` — 호스팅 미정 |
| 6-17 | **`landmarks.json_v1.1` 예시 불일치** | 두 예시 모두 `"id": 1`, 두 번째는 `image/description` 필드 사용 (스키마 불일치) |
